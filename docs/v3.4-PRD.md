## 一、文档目的与范围

### 1.1 目的
本文档承接 v3.3.9 综合优化收尾，规划 v3.4 阶段的后续演进方向。v3.3.1-v3.3.9 已完成"前端体验完善"（四角色体验闭环 + 管理员能力 9/9 全覆盖），v3.4 转向"后端能力补齐 + 全平台闭环"，并将 AI 平台作为统一外部数据写入入口。

### 1.2 范围
- v3.3.9 已落地项的后续后端配套（积分兑换扣分闭环 / streak 真实计算 / 微信配置持久化）
- 平台级能力补齐（推送通道 / 操作审计 / 任务指派）
- 体验增强项（健康趋势 / AI 分析 / 新闻收藏 / 纪念日扩展）
- **统一外部数据写入 Skill**：通过 AI 平台定时任务，周期性抓取外部数据并写入平台 token 保护接口

### 1.3 不在本版范围
- 多家庭租户隔离（列入 v3.5+）
- 微信扫码登录完整方案（OAuth2，列入 v3.5+）
- 前端框架迁移（原生 JS → Alpine.js，列入 v3.5+）

## 五、P0 需求详解

### P0-1 ｜ 积分兑换后端扣分闭环

**需求描述**：v3.3.9 已建前端闭环（localStorage 记录 + admin 确认/驳回），但积分未真正扣减。v3.4 补后端兑换记录表 + 扣分接口 + 审批流，前端 localStorage 记录迁移至后端。

**用户故事**：作为孩子，我兑换"30 分钟游戏时间"后，我的积分余额真正减少 50 分；作为爸妈，我能在前端审批兑换申请，确认后扣分生效。

**数据模型**：
```
redeem_records
  id          INTEGER PK
  member_id   INTEGER NOT NULL      -- 兑换人
  item_id     INTEGER              -- 兑换商品 ID（可空，自定义商品）
  item_name   TEXT NOT NULL        -- 商品名称（冗余，防商品下架）
  cost        INTEGER NOT NULL     -- 消耗积分
  status      TEXT NOT NULL DEFAULT 'pending'  -- pending/confirmed/rejected
  approver_id INTEGER              -- 审批人（admin）
  created_at  DATETIME
  approved_at DATETIME
```

**API 设计**：
- `POST /api/points/redeem`（成员自助）— 创建兑换记录（status=pending），校验积分余额
- `GET /api/points/redeem?member_id=&status=`（查询）— 列表，member 可查自己，admin 可查全部
- `PUT /api/points/redeem/:id/approve`（admin）— 确认，扣减 points_records + 更新 status=confirmed
- `PUT /api/points/redeem/:id/reject`（admin）— 驳回，status=rejected，不扣分

**验收标准**：
1. 兑换后记录写入 redeem_records，status=pending
2. admin 确认后扣分，成员积分余额减少 cost
3. admin 驳回后不扣分，记录标记 rejected
4. 积分不足时兑换被拒（400）
5. 前端 localStorage 记录可一键迁移至后端

**优先级理由**：三角色（妈妈/爸爸/小朋友）两轮遗留最高优先项，前端入口已就绪，投入产出比最高。

### P0-2 ｜ streak 后端真实计算

**需求描述**：v3.3.6 前端兜底显示"今日有完成=1天"，v3.4 补后端跨日累计真实计算。

**用户故事**：作为爸爸，我看到"连续打卡 7 天"是真实累计的，而不是前端兜底的 1 天。

**数据模型**：复用 chorse_records（已完成记录表），按 `completed_at` 跨日累计连续天数。

**API 设计**：
- `GET /api/chorse/streak?member_id=` — 返回 `{streak: 7, last_date: "2026-07-17"}`
- 计算逻辑：从今日倒推，若某日有 completed 记录则 +1，遇到空日则中断
- `GetChorseDashboardHandler` 填充 `stats.streak` 字段（当前为默认 0）

**验收标准**：
1. 连续 N 天有完成 → streak=N
2. 中断一天 → streak 归零重计
3. 今日未完成但昨日完成 → streak 保持昨日值（不 +1）
4. 前端兜底逻辑退场（删除 v3.3.6 的 streak 兜底代码）

**优先级理由**：爸爸视角头号数据困惑，前端兜底是临时方案，后端真实计算才能彻底解决。

### P0-3 ｜ 微信配置持久化

**需求描述**：v3.3.9 微信配置面板为运行时内存态，重启丢失。v3.4 持久化到 data_source_config 表。

**用户故事**：作为管理员，我配置的微信 Webhook 重启后仍然生效。

**数据模型**：复用 `data_source_config` 表（source_type='wecom'），存 webhook_url / enable_push。

**API 设计**：
- `GET /api/wecom/config`（已注册，v3.3.9）— 改为读 DB（当前读内存）
- `PUT /api/wecom/config`（已注册）— 改为写 DB（当前写内存）
- 启动时 `SetWeComConfig` 从 DB 加载（当前从 config.yaml）

**验收标准**：
1. 保存配置后重启服务，配置仍在
2. 多实例部署时配置共享（同一 DB）
3. 内存态作为 DB 读取缓存，写入同步落 DB
4. UI 文案移除"仅运行时内存态"警告

**优先级理由**：v3.3.9 已建前端入口但内存态限制明显，持久化是自然延伸。

### P0-4 ｜ 统一外部数据写入 Skill（AI 平台定时写入）

**需求描述**：部分接口（news / calendar / anniversary / weekend proposals）依赖外部数据定期插入，当前需零散外部脚本（Python + cron）各自实现。v3.4 提供"统一数据写入 Skill"能力：通过 AI 平台（Trae）的定时任务调度，周期性抓取外部数据并统一写入平台 token 保护接口，替代零散脚本。

**用户故事**：作为管理员，我希望 AI 平台每天自动抓取 RSS 新闻、每周同步纪念日、每日推荐休闲活动，统一写入平台，无需我自己维护外部脚本和 cron。

**能力设计**：
- 复用已有外部写入接口（无需新增后端接口）：
  - `POST /api/external/news/batch`（scope: news:write，source_url 去重 upsert）
  - `POST /api/external/calendar/events`（scope: calendar:write）
  - `POST /api/external/anniversaries`（scope: anniversary:write）
  - `POST /api/external/weekend/proposals`（scope: weekend:write）
- AI 平台定时任务（Trae Schedule）作为统一写入入口：
  - 每个数据源一个定时任务，携带目标 API Token + scope
  - 任务执行：AI 抓取外部数据 → 转换为接口 schema → 调用写入接口
  - 去重：news 用 source_url upsert，calendar 用 title+date，anniversary 用 title+date
- 统一 Token 管理：管理员在 Token 面板创建"AI 平台写入 Token"（scope 按需组合），明文 token 配置到定时任务

**数据模型**：无新增表，复用 api_tokens + 各业务表。

**API 设计**：无新增接口，复用 `/api/external/*` 写入接口（见 `docs/v3.3-API.md` 第四节）。

**Skill 任务模板**（AI 平台定时任务 message 内容规范）：
```
任务：抓取 <数据源> 写入 HomeMate <接口>
- 数据源：<RSS URL / API endpoint / 爬虫目标>
- 目标接口：POST /api/external/news/batch
- API Token：hm_xxx（scope: news:write）
- 去重键：source_url
- 频率：每小时 / 每日 09:00 / 每周一 09:00
- 失败重试：3 次，间隔 5 分钟
- 输出：写入条数 + 失败原因（写入 /workspace/.trae/logs/ 或 toast 通知）
```

**验收标准**：
1. AI 平台定时任务按配置频率执行，数据成功写入对应接口
2. 重复数据被去重（source_url / title+date）
3. Token 失效时任务失败并通知管理员（不静默失败）
4. 管理员可在 Token 面板查看该 Token 的 last_used_at 确认任务在运行
5. 任务执行日志可查（写入条数 / 失败原因）

**优先级理由**：用户明确要求"提供统一 skills 能力通过 AI 平台导入可定期写入数据"。当前外部写入接口已就绪但缺统一调度入口，AI 平台 Skill 能力是最佳承载——替代零散脚本，统一鉴权，统一监控。

**实施路径**：
1. 管理员创建专用 API Token（按数据源 scope 组合）
2. 配置 AI 平台定时任务（Schedule 工具，cron 表达式 + message 含数据源/接口/token）
3. AI 平台按频率执行：抓取 → 转换 → 写入 → 记录结果
4. 管理员通过 Token 面板 last_used_at + 任务执行日志监控

## 六、P1 需求详解

### P1-1 ｜ 推送通道建设

**需求描述**：当前推送仅 WeCom Webhook MVP（内存态），家务认领/到期/异常无主动推送。

**能力设计**：
- 扩展 Pusher 接口：新增 EmailPusher / SMSPusher（依赖 P0-3 持久化后的通道配置）
- 推送触发点：家务认领通知、deadline 到期提醒、健康异常告警、积分变动
- 调度器新增 `notificationPushLoop`（已有 reminderScanLoop 基础）

**API 设计**：
- `PUT /api/wecom/config` 扩展：支持 email_config / sms_config 字段
- `GET /api/notifications/pending` — 查看待推送通知队列

**验收标准**：家务认领后被认领人收到推送；deadline 前 30 分钟提醒；健康异常告警。

### P1-2 ｜ 操作审计日志

**需求描述**：误删/误改无法追溯，多人家庭责任不清。

**数据模型**：
```
operation_logs
  id          INTEGER PK
  user_id     INTEGER          -- 操作人
  username    TEXT             -- 操作人用户名（冗余）
  method      TEXT             -- HTTP 方法
  path        TEXT             -- 请求路径
  body_summary TEXT            -- 请求体摘要（截断 500 字）
  ip          TEXT             -- 来源 IP
  status_code INTEGER          -- 响应码
  created_at  DATETIME
```

**能力设计**：Gin 中间件 `AuditLogMiddleware`，记录所有 POST/PUT/DELETE 写操作。

**API 设计**：
- `GET /api/admin/audit-logs?user_id=&path=&from=&to=`（admin）— 分页查询

**验收标准**：所有写操作有日志；admin 可按人/路径/时间筛选；日志保留 180 天。

### P1-3 ｜ 任务显式指派 + 验收人改派

**需求描述**：爸爸想"把洗碗指派给小明"，当前只能成员自己认领；验收人自动指派后无法更改。

**数据模型**：`chorse_tasks` 表加 `assignee_id` / `reviewer_id` 字段（可空，空=待认领/自动指派）。

**API 设计**：
- `PUT /api/chorse/tasks/:id/assign` — 指派给指定成员（admin）
- `PUT /api/chorse/tasks/:id/reviewer` — 更换验收人（admin）

**验收标准**：管理员可指派任务；验收人可更改；前端任务卡显示指派人/验收人。

## 十一、非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | 列表接口 P95 < 200ms；趋势聚合接口 < 500ms |
| 安全 | 所有写操作需鉴权；操作审计覆盖 100% 写操作；API Token 明文不落日志 |
| 可观测性 | 调度器状态可查；AI 平台 Skill 任务执行日志可查；Token last_used_at 实时更新 |
| 数据备份 | 新闻/日历/成员支持 CSV 导出（v3.3.9 已落地）；积分记录/家务记录导出列入 v3.4.1 |
| 兼容性 | 数据模型变更需 migration 脚本；前端向后兼容旧接口响应 |
| 可用性 | AI 平台 Skill 任务失败重试 3 次；Token 失效通知管理员不静默失败 |

## 十二、风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| AI 平台 Skill 任务依赖外部数据源可用性 | 数据写入中断 | 失败重试 + 通知管理员 + 降级用上次成功数据 |
| LLM 接口成本（P2-2） | AI 分析预算超支 | 按需触发（非自动）+ 缓存分析结果 |
| 微信 OAuth2 审核周期长 | 推送通道延期 | P1-1 先用 Webhook，OAuth2 列入 v3.5 |
| 数据模型变更影响线上数据 | migration 失败 | 备份 + 灰度 + 回滚脚本 |
| 多 Skill 任务并发写入冲突 | 数据重复/竞态 | source_url 去重 upsert + 幂等设计 |
