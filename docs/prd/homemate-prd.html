SECTION 01

需求背景

一个典型的四口之家，日常运转中充斥着大量低效的信息传递: 健康数据散落在各自的智能手表 App 里，家务分工全靠口头约定，周末去哪玩每次都要在微信群里讨论半天，孩子的锻炼和家务完成情况没有统一的记录和激励手段。这些事情单独来看都不大，但累积起来消耗了大量家庭沟通成本。

当前家庭数字生活的核心矛盾在于: 家庭成员的健康、出行、劳动、财务等信息分布在各自独立的平台和设备上，没有一个地方能把这些数据汇聚起来，形成完整的家庭视图。父母查看孩子今天的运动情况需要打开另一个 App，老人想知道自己血压趋势找不到历史记录，想给家务做得好的孩子一个奖励也缺乏量化的依据。

市面上的产品要么聚焦于个人健康（如 Apple Health、Garmin Connect），要么聚焦于家庭社交（如家庭微信群），要么聚焦于儿童教育激励。没有任何一个产品把"健康监测 + 家务协作 + 出行规划 + 积分激励"这几个家庭高频场景串联起来，形成闭环。

核心假设: 家庭需要一个统一的协作平台，将分散在多个设备和 App 中的健康、家务、出行等信息汇聚到一处，用游戏化的积分机制连接各个场景，让家庭成员之间的协作变得可见、可量化、可激励。

HomeMate v3.0 正是为解决这一问题而构建。基于 MCP（Model Context Protocol）协议，系统能够对接 Garmin、Apple Health、华为健康等多种数据源，通过统一的 Service 层聚合数据，在 Web 端和微信公众号两个渠道为家庭成员提供一致的使用体验。

SECTION 02

产品定位与目标用户

产品定位

HomeMate 是一个面向家庭的协作平台，以健康数据聚合为核心，向家务分工、出行规划、积分激励等场景延伸。它不是一个替代 Garmin Connect 或 Apple Health 的健康 App，而是一个家庭级别的"数据中台"——把各个成员、各个设备、各个渠道的数据收拢到一处，让家庭协作有据可依。

F1 — 家庭健康总览

graph LR subgraph 数据源 G[Garmin 手表] H[华为手环] A[Apple Health] M[手动录入] end subgraph MCP 层 GM[garmin-mcp] HM[health-mcp] end subgraph Service 层 SVC[HealthMonitor] STORE[HealthStore] end subgraph API 层 API1[/health/summary] API2[/health/real] API3[/health/sync] end G --> GM --> SVC --> STORE H --> HM --> SVC A --> SVC M --> SVC SVC --> API1 SVC --> API2 SVC --> API3

业务逻辑

  • 系统从已配置的数据源获取每个成员的健康数据，按日聚合存储到 health_data_cache 表
  • Garmin 数据通过 garmin-mcp 子进程以 stdio 方式通信，调用 getDailyHealth 工具获取当日数据
  • 华为/Apple Health 数据源预留接口，HealthMonitor 已实现 SyncHuaweiData 方法，待对应 MCP Server 接入
  • 健康评估规则: 周均步数 ≥ 8000 且周均睡眠 ≥ 7h → "优秀"；周均步数 ≥ 6000 且周均睡眠 ≥ 6h → "良好"；周均步数 ≥ 4000 且周均睡眠 ≥ 5h → "一般"；其余 → "需关注"

交互逻辑

  • 进入 Dashboard 页面，默认展示"今日健康"卡片组，每个成员一张卡片
  • 卡片包含 9 项指标的当日值，无数据显示 "--"
  • 点击"同步数据"按钮，触发增量同步（调用 /health/sync），同步期间显示加载状态
  • 支持点击指标查看近 7 天趋势

规则约束

  • 数据源配置: source_type 枚举值 garmin / apple_health / huawei / manual
  • API Key、API Secret 字段在列表接口中脱敏显示（仅展示前 4 位）
  • 同步操作有 30 秒超时保护（配置项 mcp_timeout）

F2 — 家务劳动系统

业务逻辑

  • 预定义 10 种家务任务，每种任务有固定的分类（cleaning/cooking/laundry/organizing/other）、难度（easy/medium/hard）和积分奖励（5-25 分）
  • 任务流程为: 成员认领 → 标记完成 → 其他成员监督确认 → 确认通过后自动调用 points.AddPoints() 加分
  • 认领时记录认领人、认领时间、截止时间（默认 24 小时）
  • 只有状态为 completed 的认领记录才能被确认

交互逻辑

  • Dashboard 展示任务网格（图标 + 名称 + 积分），点击任务卡片弹出认领确认框
  • 认领成功后任务进入"我的待办"列表，状态标签显示"待完成"
  • 完成待办后状态变为"待确认"，其他成员看到确认按钮
  • 确认通过后弹出积分奖励提示，任务归档到"今日完成记录"

F3 — 积分可视化系统

业务逻辑

  • 积分按三个维度分类统计: 运动（exercise）、健康（health）、劳动（chorse），汇总为总积分
  • 等级称号和升级阈值: 总积分 ≥ 1500 → "运动新星"；≥ 2000 → "活力少年"；≥ 2500 → "全能小能手" → "活力达人"；≥ 3000 → "运动健将"（路径根据当前等级动态推算）
  • 积分来源: 家务确认完成自动加分（调用 AddPoints），运动和健康积分目前手动记录，后续通过 MCP 自动采集
  • 排行榜按总积分降序排列，同分按劳动积分再排

交互逻辑

  • 积分 Dashboard 顶部展示家庭总积分和本周目标进度环（默认周目标 500 分）
  • 中部为成员卡片列表，每张卡片展示: 姓名、总积分、三维度积分柱状条、等级称号、距下一等级所需积分
  • 底部为最近积分变动时间线，标注来源类型和分值

F4 — 周末出行推荐

业务逻辑

  • 系统预置 6 种推荐方案，每种方案包含: 标题、描述、图标、分类标签、时长、费用等级、难度、适宜人群、天气要求、出行建议
  • 投票机制: 每位成员对每个方案只能投一票，重复投票返回错误提示；支持取消投票（取消后重新统计结果）
  • 自定义方案: 任何成员可提交新方案，系统自动分配 ID 并加入候选池，参与投票
  • 确认方案: 管理员角色可确认最终选定方案，确认后推送通知全体成员
  • 投票结果按票数降序排列，票数最高的方案标记为"当前领先"

交互逻辑

  • 进入周末出行页面，顶部展示本周末日期范围和天气预报（周六/周日天气、温度、出行建议）
  • 中部为方案卡片网格，每张卡片展示图标、标题、分类标签、时长/费用/难度、投票按钮
  • 底部为投票结果柱状图，实时更新投票数和领先状态
  • "添加方案"按钮打开表单，填写方案详情后提交

权限逻辑

  • 所有家庭成员可查看方案、投票、取消投票、提交自定义方案
  • 仅 admin 角色可执行"确认选定方案"操作

F5 — 多数据源配置

业务逻辑

  • 每个家庭成员独立配置健康数据源，支持一个成员同时配置多个数据源（如 Garmin 用于运动数据、手动录入用于血压数据）
  • 数据源类型: garmin（通过 garmin-mcp stdio 通信）、apple_health（预留）、huawei（通过 health-mcp）、manual（手动录入）
  • 配置项: 数据源类型、API Key、激活状态。配置通过 POST /api/health/config 持久化到 SQLite data_source_config 表（INSERT OR REPLACE 语义，按 member_id 去重）
  • 同步操作 POST /api/health/sync 查找成员的数据源配置后，写入 health_data_cache 缓存表，同时更新配置的 last_sync_at 和 is_active
  • 健康总览 GET /api/health/summary 从数据库读取成员列表，再查询各自最新的 health_data_cache 记录，动态生成指标列表（步数/心率/睡眠/血压/体重/身高/压力/血氧/身体电量），自动检测异常并生成告警

交互逻辑

  • 在设置页面"数据源配置"卡片中管理所有成员的数据源
  • 按成员分组展示已配置的数据源列表，显示成员头像、数据源类型图标、激活状态、最近同步时间
  • 点击"+ 添加数据源"虚线按钮打开配置弹窗，选择成员（下拉）、数据源类型（下拉）、填写 API Key（可选）后保存
  • 已配置的数据源可点击"配置"修改，或点击"同步"触发数据拉取
  • 前端使用动态成员映射（memberColors/memberNames），成员颜色由 updateMemberMaps() 根据 API 返回的成员列表自动分配

认证流程

  • 用户提交用户名和密码到 POST /api/auth/login
  • 服务端验证通过后签发 JWT Token，Claims 包含 user_id、username、role、family_id
  • 后续请求在 Authorization: Bearer <token> 头中携带 Token
  • AuthMiddleware 校验 Token 有效性，RoleMiddleware 校验角色权限

F8 — 成员管理增强

业务逻辑

  • 家庭成员 CRUD：支持创建、查看详情、更新、删除成员，数据持久化到 SQLite
  • 创建成员时必须配置三个维度：角色（admin/adult/child/elder/guest）、Health 关注指标（从 9 种健康指标中勾选）、数据采集模块插件（garmin/apple_health/huawei/manual）
  • 角色决定 Dashboard 视图和权限范围（admin 看全局、adult 看自己+孩子、child 眀简化、elder 看大字版）
  • Health 关注指标决定该成员在健康总览 Tab 中默认显示哪些指标卡片
  • 数据采集模块决定该成员的数据来源：Garmin 通过 MCP 自动拉取、Apple Health 待对接、华为待对接、manual 为手动录入

交互逻辑

  • 成员列表以卡片网格展示，每张卡片包含：头像（角色色彩）、姓名、角色标签、年龄、数据源、关注指标标签
  • 新增/编辑对话框包含：姓名输入、角色下拉选择、年龄输入、9 项关注指标复选框、数据源下拉选择
  • 所有操作（增删改）通过 API 持久化到 SQLite，DB 不可用时返回错误提示
  • 删除操作通过 DELETE /api/members/:id 执行真实数据库删除

数据模型变更

  • family_members 表新增列：health_focus TEXT（逗号分隔的关注指标）和 data_source_plugin TEXT（数据源插件类型）
  • Store 层新增 UpdateMember()、GetMemberByID()、DeleteMember() 方法
  • 新增 migrate() 方法：使用 pragma_table_info 检查列是否存在，不存在则 ALTER TABLE ADD COLUMN，兼容旧数据库无需手动迁移

F9 — 大屏综合展示

业务逻辑

  • 大屏接口 GET /api/dashboard/bigscreen 聚合 4 大板块数据：家庭健康总览、今日家务、活动推荐、积分动态
  • 家务板块数据从 chorse 包的 GetTodayRecords() 和 GetMemberContrib() 动态获取，非硬编码
  • 积分板块数据从 points 包的 GetMembersSnapshot() 动态获取，按总积分排序后生成排行榜
  • 健康板块从数据库读取成员和各自最新的健康缓存，动态生成指标和状态色标（green/yellow/red），底部显示告警
  • 活动推荐板块显示周末天气 + 方案卡片（领先标记），方案数据来自 weekend handler 的 proposals 变量
  • 前端以卡片式布局展示各板块，页面加载时自动调用 API 获取聚合数据

  • 大屏 Tab 在导航栏中独立入口，与各功能 Tab 平级

SECTION 04

用户场景

场景一: 每日健康监测

妈妈早上起床后打开 HomeMate，查看全家人的健康状态。爸爸的 Garmin 数据已自动同步，老人的血压需要手动录入，孩子的运动数据来自前一天的记录。

1

打开健康总览

妈妈进入 Dashboard，看到四张成员健康卡片。爸爸的卡片显示步数 8,234、心率 72bpm、睡眠 7.2h，数据来源标注 "Garmin - 今日 06:30 同步"。其他成员数据来源标注"手动录入"。

2

录入老人血压

妈妈切换到老人（爷爷）的健康卡片，点击"录入数据"，选择"血压"指标，输入收缩压 128 / 舒张压 82，提交后数据保存到 health_records 表。

3

查看周趋势

点击爸爸的"步数"指标，展开近 7 天步数折线图，确认本周运动量稳定。健康评估标签显示"优秀"（绿色）。

4

同步 Garmin 数据

点击"同步数据"按钮，系统调用 /health/sync，通过 garmin-mcp stdio 进程获取爸爸的最新数据。同步完成后刷新 Dashboard。

场景二: 周末出行投票

周四晚上，全家讨论这周末去哪里玩。爸爸打开 HomeMate 的周末出行页面，看到 6 个推荐方案和天气预报，全家在系统里投票决定。

1

查看推荐方案

爸爸进入周末出行页面，顶部显示"本周末: 2026-07-19 ~ 07-20"，天气预报: 周六晴 28-35°C，周日多云。6 个方案卡片按分类排列。

2

家庭成员投票

爸爸投了"西湖骑行"（天气晴适合户外），妈妈投了"浙江省博物馆"（免费且室内），儿子和女儿投了"湘湖露营野餐"。投票结果实时更新: 湘湖露营 2 票领先。

3

女儿提交自定义方案

女儿觉得现有方案都不错，但又想到"室内攀岩体验"。点击"添加方案"，填写详情后提交，新方案立即出现在候选池中参与投票。

4

爸爸取消并重投

爸爸看到湘湖露营领先，觉得天气太热不适合露营。取消自己之前的投票，改投"室内攀岩体验"。结果更新: 湘湖露营和室内攀岩各 2 票并列。

5

妈妈确认最终方案

作为 admin 角色，妈妈查看投票结果后确认"室内攀岩体验"为最终方案。系统记录选定方案，准备推送通知。

场景三: 家务积分激励

儿子主动倒了垃圾和整理了房间，希望通过完成家务获取积分，冲击排行榜第一。爸爸作为监督者确认完成情况。

1

儿子认领任务

儿子打开家务面板，看到任务网格。选择"倒垃圾"（5 分）和"整理房间"（15 分），点击认领。两条认领记录进入待办列表，状态为"待完成"。

2

标记完成

儿子完成两项家务后，在待办列表中点击"标记完成"。状态变为"待确认"，等待其他家庭成员监督确认。

3

爸爸监督确认

爸爸在"待确认"列表中看到儿子的两条记录，确认垃圾已倒、房间已整理后，点击"确认完成"。系统调用 points.AddPoints("儿子", "chorse", "劳动", "倒垃圾", 5) 和 points.AddPoints("儿子", "chorse", "劳动", "整理房间", 15)，总计增加 20 分。

4

查看积分变化

儿子查看积分面板，总积分从 1,520 增长到 1,540，距离下一等级"活力少年"还差 460 分。积分时间线新增两条记录: "倒垃圾 +5"和"整理房间 +15"。排行榜中儿子的排名不变（第 4 名），但与第 3 名差距缩小。

三层架构说明

Handler 层（接入层）

负责 HTTP 请求处理、参数校验、响应格式化。当前 13 个 handler 模块，覆盖认证、健康、家务、积分、出行、成员、日历、聊天、微信、IoT、反馈、Dashboard 等功能。所有 handler 返回统一 JSON 格式: {"code": 0, "message": "success", "data": {...}}。DB 实例通过 NewRouter(db) 参数注入，在路由注册前添加 Gin 中间件将 DB 设置到 gin.Context 中，handler 通过 c.Get("db") 获取。chorse、points、weekend 使用内存存储（包级变量），成员管理和数据源配置通过 Store 层持久化到 SQLite。大屏 Dashboard 通过跨包函数调用（chorse.GetTodayRecords()、points.GetMembersSnapshot()）聚合真实数据。

Service 层（业务层）

负责业务逻辑、数据聚合、外部服务调用。8 个 Service 模块: agent（AI 对话引擎）、trip（出行规划）、health（健康监测）、diet（饮食营养）、finance（财务追踪）、knowledge（知识库管理）、calendar（日历同步）、iot（智能家居控制）。Service 层通过 MCP Manager 调用外部 MCP Server 获取数据，通过 Store 层持久化到 SQLite。

Store / MCP 层（基础设施层）

Store 层封装 SQLite 数据库操作，提供 CRUD 接口。MCP Manager 包含两部分: Registry（服务注册表，维护所有 MCP Server 的配置和能力元数据）和 MCPClientManager（客户端连接池，管理多个 MCP Server 的连接、工具调用和生命周期）。当前已注册 3 个 MCP Server 子进程: garmin-mcp、health-mcp、weather-mcp，均通过 stdio 方式通信。

MCP Manager 工作机制

  • 注册阶段: 启动时从配置文件读取 MCP Server 列表，调用 Registry.Register() 注册每个 Server 的名称、传输方式（stdio/sse）、命令、参数、分类和工具列表
  • 连接阶段: 调用 MCPClientManager.Connect() 启动子进程（stdio）或建立 HTTP 连接（sse），发送 InitializeRequest 完成握手
  • 调用阶段: Service 通过 CallTool() 传递 Server 名称、工具名称和参数，MCP Manager 路由到对应连接并转发请求
  • 分类路由: Registry 支持按 Category（weather/health/flight/map/iot/food/knowledge/calendar）查找 Server，Service 可按需发现同类服务的多个实例
